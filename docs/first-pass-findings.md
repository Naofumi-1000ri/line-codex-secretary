# 1周目セットアップ所感

実施日: 2026-09-03

## 利用者案内

- 「一度に一つ」をクリック単位に分解すると、確認回数が増えて流れが分かりにくくなった。
- 名前、団体名、業種、通常の選択、URL入力、保存、検証はAIがまとめて行う。
- 利用者へ渡すのは、ログイン、MFA、規約同意、OAuth承認、秘密情報の表示・入力など本人しか確定できない境界に限る。
- 複数クリックでも同じ目的で途中判断が不要なら、一つの操作としてまとめて案内する。
- LINE公式アカウント作成では、連絡先メールアドレスの直接入力だけで停止すると不要な往復が増えた。メールアドレス入力、入力内容・規約の確認、同意できる場合の `[確認]` までを一つの目的として案内し、確認画面への遷移はAIが検証する。確認画面での最終作成は別の本人判断として残す。
- LINE公式アカウントの確認画面では、任意の情報配信アカウントの友だち追加が既定で選択される場合がある。Bot構築には不要なので既定値をオフとし、利用者が明示的に希望した場合だけオンにする。
- LINE公式アカウント作成時の画像CAPTCHAで、AIが「自動車」に該当するマスを案内したところ誤判定した。CAPTCHAはもともと本人確認の境界でもあるため、AIは問題の分類やマス指定をせず、表示内容に従う操作全体を利用者へ引き継ぐ。
- LINE公式アカウント作成フォーム、Business Manager、Official Account Managerの3タブとreCAPTCHAを並行して開いていた途中でCodexブラウザが終了した。因果関係は断定できないが、再発防止としてLINE関連は原則1タブで進め、完了済みタブは非秘密IDを記録後に閉じる。終了後は作成済み状態を再検証し、未完了画面だけを復元する。
- 作成後、管理画面へ入る前に追加同意が2回続いた。一度の同意で完了とみなさず、各同意を独立した本人判断として案内し、対象アカウントの管理画面URLとホーム画面が表示されるまで再検査する。
- 2回目のドキュメント試験では既存リソースが見つかるのが正常である。「既存があります。使いますか」と再利用へ進むのは判定ミスだった。既存確認より先に `create_isolated` を固定し、既存は名前衝突と誤接続の検査だけに使う。
- 「アカウントは既存でよいが、BotとCloudflareは新規」というドキュメント試験では、既存ビジネスマネージャー組織やProviderを選ぶと新旧の構成が接続されてしまう。`create_isolated` ではLINE Business IDとCloudflareアカウントだけを再利用し、LINE公式アカウント、LINEビジネスマネージャー組織、Provider、Messaging API Channel、D1、Workerをすべて新規にする。
- ビジネスマネージャーの新規組織画面ではビジネスタイプが「法人」「個人事業主」に限定され、LINE公式アカウントの業種 `個人 → 個人（架空）` とは別の区分だった。利用者が個人事業主を選ぶと、屋号、フリガナ、事業主名、住所、WebサイトURL、電話番号、メールアドレスなど実在情報の必須欄が追加された。これらは会話へ貼らせず公式フォームへ直接入力してもらう。
- 必須の実在情報をすべて利用者へ入力依頼すると詰まりやすい。個人用の既定案は日本、個人事業主、試験ID付き組織名とし、屋号、事業主名、住所、Webサイト、電話、メールは同じLINE Business ID配下の既存組織から新規試験組織へ複写する案を先に示す。「この内容でいいですか？」と一度確認し、了承後にAIが入力する。これは既存組織との接続ではない。
- 複写元がない空の新規アカウントも定義した。屋号 `PC Codex秘書`、フリガナ `ピーシーコーデックスヒショ`、Webサイトは公開GitHubリポジトリを提案し、事業主名、住所、電話、メールなど捏造できない事実だけを公式フォームで一度に入力してもらう。項目ごとの往復を避け、最終送信前に提案値を含む全体を一度確認する。
- ビジネスマネージャー組織の `[同意して作成]` を押すと中間の確認画面は表示されず、組織が即時作成されてメール認証へ移った。AIは押下前に必須欄と試験専用の組織名を検査する。利用者が先に押した場合も発行済みの新規組織IDを検証して続行し、重複作成しない。アカウント・チャネル接続は確認メールの認証完了後に行う。
- 新規組織ごとのメール認証は、ログイン済みでも省略できず、AIだけでは越えられない高摩擦な本人操作だった。`create_isolated` の事前条件に「登録メールの受信箱をその場で開ける」を追加し、利用できなければ個人情報入力・組織作成前に停止する。
- 新規ProviderのAPI利用規約へ同意した後、プライバシーポリシーURLと利用規約URLの登録画面が表示された。どちらも任意で後から変更できるため、指定がなければURLを捏造せず空欄で進め、Provider／Channelを確定する `[OK]` は本人へ引き継ぐ。
- Provider／Channelの確定には `[OK]` が2回必要だった。1回で完了とみなさず、Messaging APIのステータスが `利用中` になりChannel IDが表示されるまで再検査する。
- Messaging API有効化後の管理画面はChannel Secretを平文で自動表示した。「AIに見えたら即失敗・必ず再発行」とすると、認証済み管理画面のブラウザ操作が成立しにくい。表示と取得・保存・送信を区別し、偶発的に画面取得へ含まれた値は再掲・保存・転送せず、利用者が公式画面からSecret Brokerへ直接渡す。再発行は権限外への送信、意図しない保存、またはAIからの完全隔離が要件の場合に行う。
- Workerの公開Webhook URLは秘密情報ではないため、AIがLINE Developersの入力欄へ自動入力して保存できた。利用者へURLのコピーや貼り付けを依頼せず、保存後に入力欄が編集不可になったことを画面で検証する。
- Webhook利用スイッチをオンにした直後に検証や再読み込みを行うと、保存通信が完了せずオフへ戻った。オンにして数秒待ち、再読み込み後もオンであることを確認してから検証する順序に変更した。

## ブラウザと認証

- アプリ内ブラウザからWranglerの `localhost` OAuth callbackへ接続できなかった。単なる待ち時間ではなく接続拒否だった。
- Wranglerのdevice authorization flowで認証できた。対象Account IDと必要scopeは `wrangler whoami` で検証する。
- 今回はWranglerが認証済みで、Cloudflareダッシュボードを開かずD1とWorkerを作成できた。そのため、初めてCloudflareを使う利用者に必要な無料アカウント作成、確認メール、MFA、OAuth、Workers利用規約、`workers.dev` サブドメイン初期設定が試験経路から抜けていた。認証済み／アカウントあり・Workers未設定／アカウントなしの3経路を標準手順へ追加した。
- `workers.dev` サブドメインは公開・世界一意のアカウント共通設定であり、Worker名とは別に利用者の確認が必要である。一方、WorkerとD1は `create_isolated` の試験ごとに新規作成する。名前候補を項目ごとに尋ねず、Account ID、Worker名、D1名、サブドメイン候補をまとめて一度だけ確認する。
- Codex再起動前は新規ブラウザタブとターミナルパネルが画面へ反映されなかった。再起動後は、必要時に表示確認してから利用する。

## 実装で見つかった問題

- macOS `security add-generic-password -w` の非TTY入力では空のパスワードが保存された。Security frameworkを使うSwift helperで、標準入力からKeychainへ保存するよう修正した。
- Secret Brokerの待機PTYをCodexターミナルへ表示する引き継ぎが失敗し、通常のシェルへアクセストークンが貼られてコマンドとして表示された。ターミナルを開いたことと専用プロンプトが表示されたことを区別し、利用者が非表示プロンプトの文言を確認するまで値を貼らせない二段階手順に変更した。通常シェルへ誤貼付した値は使用せず、発行元で直ちにローテーションする。
- LINE管理画面の `[コピー]` とmacOSクリップボードを一時経路にすれば、利用者がターミナルへSecretを貼る必要はない。Brokerへ `--clipboard` を追加し、AIが値を読み取らず `pbpaste` から `wrangler secret put` の標準入力へ渡し、成功・失敗にかかわらず `pbcopy` でクリップボードを消去する方式を既定にした。
- OSの自動起動ではCodexの実行環境が利用者のターミナルと異なり、設定と診断が分かりにくくなった。自動起動は採用せず、`npm run secretary` を明示的に実行し、`Ctrl+C`で止める構成へ変更した。
- 依頼ごとに独立したCLIプロセスを作る方式では会話が分かれた。Codex App Serverを前景で1つ起動し、LINEトークごとのthread IDへ再接続する方式へ変更した。
- 再試行時に同じidempotency keyを使うと、2回目の失敗遷移が重複扱いになりジョブがLEASEDで残った。試行ごとにUUIDを使うよう修正した。
- Worker公開前に `workers.dev` subdomainが未登録でdeployが止まった。既存subdomainの確認後に再deployすると成功した。

## 1周目の結果

- LINE → Webhook → D1 → PC Agent → Codex CLI → LINE返信が成功した。
- 最終依頼は1回で完了し、通知も1回送信された。
- workspaceは `LineBotV2`、実行モードは読み取り専用、所有者は1人で開始した。
- PC Agentはバックグラウンド登録せず、利用者が秘書を使う間だけターミナルで起動する。
- App Server移行後、連続するLINE依頼2件が同じthread IDを使い、2件目が1件目の内容を正しく引き継ぐことをD1と応答内容で確認した。
